# Changelog

## 0.2.1 — 2026-09-20

- `siftr ack <SIGNAL>` is the one way to answer a signal, and `siftr dismiss` is gone. The two verbs asked the same question twice and neither answered it: `ack` recorded a row that nothing read — a trialist ran `ack`, then `changes`, and got byte-identical output in both text and `-j` — while `dismiss`, the only lever that stopped a reminder, failed silently on any signal that had recurred, which is exactly when a developer most wants it. Now `siftr ack sN -m why` means "I'm dealing with this" and `siftr ack sN --wrong -m why` means "siftr shouldn't have raised this". **Both end the `still open:` reminder**, because the developer has answered either way, and the command says `no longer reminded of this change` on the spot. One judged signal silences its whole change, since the group is one thing to the developer. The ledger still writes two distinct kinds, `acked` and `dismissed`: `dismissed` is the only record anywhere that a signal was judged *wrong*, which is the single input a precision measurement needs (`docs/findings/attention.md` §4). So the interface collapsed and the evidence did not. Nothing stored changes, and no rule, threshold or confidence formula moved.
  - Upgrading: replace `siftr dismiss sN` with `siftr ack sN --wrong`. In `history --signals -j`, `dismissed: true` is replaced by `judged`, which is `"acting"`, `"wrong"` or null — a boolean could not carry `"acting"`, which is information no field held before. `outcome` is unchanged and still describes the change rather than the verdict on siftr, so a signal called wrong still reads `open` while it is there.
- A judgement holds however many times the change comes back. The verdict read a signal's feedback only up to the run it **first** resolved in, so a regression that resolved in r7 and returned in r8 ignored any `ack` or `dismiss` made afterwards: the row was stored, `history --signals` never printed it, and the reminder came back on every subsequent return. A judgement naming the signal is now read however long after the fact it was made. An *investigation* still is not: `resolved after investigation` is a claim about what brought the fix about, and an `explain` run after the fix cannot back it — so `judged: "wrong"` alongside `investigated: false` is the ordinary shape for a signal answered after it had already gone away. `tests/flap.rs` covered only the case where the judgement precedes the first resolution, which is why the guard stayed green while the behavior was broken.
- One command for either kind of id: `siftr explain <ID>` takes a signal id (`s3`) or a behavior id (4 to 16 hex digits), and `siftr evidence` is gone. The split was real inside siftr and invisible outside it — `explain` already printed evidence, and each command's `next:` line walked the reader to the other, which is the only reason anyone used both. The two id shapes cannot collide (`s` is not a hex digit), so nothing has to be disambiguated. `--run` and `-n` now apply to both halves, closing the asymmetry that made `siftr explain s1 --run r4` an argument error while `evidence` accepted it. On a signal, `--run` takes the lines from another of the runs that signal was compared over and refuses any other, so evidence stays traceable to the comparison it belongs to; on a behavior it picks any run, as `evidence` always did. A signal's report now also names its capture files, which only `evidence` used to, so nothing the old two-step reached needs a second command. `siftr summary`'s `next:` hint says `explain` where it said `evidence`.
  - Upgrading: replace `siftr evidence X` with `siftr explain X` — same arguments, same flags, and `-j` returns the same document. There is no alias; typing the retired name answers with the replacement to run. `explain -j` now emits one of two documents, told apart by their keys (`signal` and `rule` for a signal, `behavior` and `stats` for a behavior), and gains `evidence.captures`. Nothing stored changes.
- Confidence is `-j` only: no human output prints it. `siftr changes` was relabelled in 0.1.6 and `siftr explain` was missed, so it still opened with `conf 0.83` and then printed the formula on its `rule` line — and a developer trialling siftr ranked signals by it, which is what a 0-1 score sitting where severity belongs invites. It measures AUC 0.43 at that job, below chance, with 92% of signals carrying exactly `(n+1)/(n+2)` and a tie-break that has never broken a tie (`docs/findings/confidence.md`). `explain`'s header drops it, and `rule` now says why the rule fired and stops there — in `-j` too, where `signal.confidence` is still the number. The change report says `most important first` once, on runs with more than one change to order. Nothing is added in its place: signals were already printed in rank order, so the order is the answer. Anything grepping `conf ` or parsing a confidence out of `-j`'s `rule` string needs updating; `signal.confidence` is unchanged.
- The first run of a context says what siftr was able to read there: which sources fed it, which did not and why, and what each absence makes unreportable — no per-example timing and no scope to attribute a log line to an example; no SQL or request lines, so no query-count or query-latency change can be found. A developer trialling siftr concluded it had little to offer, never having seen a FREQUENCY or LATENCY signal fire, because their project had no SQL or HTTP telemetry at all — a limitation `siftr sources` would have told them upfront and nothing else did. Said once per context rather than on every run, and silenced by `--no-report` and `--quiet-unless-changed` like any other siftr output. Under `-j` it goes to stderr; the run document on stdout is unchanged.
- A command that quietly starts a new baseline beside a context that already has history now says so, naming that context and giving the rule in the same breath: a baseline is keyed on the project and the command as you typed it, so `bundle exec rspec spec/models` starts from nothing rather than joining `bundle exec rspec`. Two developers guessed that rule wrong in two separate trials — the second *after* it had been moved to the README's opening in bold, which is evidence that a fact learned three hours upstream is not available at the moment it is needed. It is now also in the long help of both commands that take `--context`. A project where nothing else has run stays quiet: a first run there is just a first run.
- `siftr run --help` now says that `-q` quiets the wrapped command rather than siftr's own report, and points at `--quiet-unless-changed` and `--no-report` for the other meaning. The flag keeps its behavior: unlike the two above, that confusion announces itself — you lose the output you were reading and go straight to `--help` — so it is a paper cut rather than a silent wrong answer.
- A red `cargo test` run reads like a red RSpec run: the failure named, as a failure, alone. libtest's lines were plain `log` behaviors, so `test X ... FAILED` was a *different behavior* from `test X ... ok` rather than the same test with another outcome; nothing carried an outcome for the ERROR rule to fire on; and the suppression that keeps a reporter's own rendering out of the report — the one that silences RSpec's progress dots — never switched on, because it asks whether the run produced any `test.example` at all. One broken test in this repo's own gate reported **18 changes in 18 groups**: the `FAILED` line, the panic, `failures:`, cargo's two `error:` lines, `test result: FAILED`, and one change per line of the assertion message. It now reports **1**, an ERROR naming the test. A `cargo` interpreter reads the two lines libtest writes about a test — the verdict becomes an outcome, so a test's identity no longer moves with its result — and `test result:` becomes a `test.summary` carrying the counts that tell a filtered run from a complete one. Everything else a run prints is still recorded and still queryable in `siftr summary`; it is no longer judged, exactly as RSpec's stdout is not. Cargo's `error: test failed, to rerun pass …` notice is dropped rather than kept: it names the *target*, so each target's first failure would be a new behavior forever while saying less than the failed test beside it — `error: could not compile …`, and a harness that aborts without reporting a failure, have no test to speak for them and stay changes of their own. A side effect worth naming: this retires a plural split. Adding one test to a one-test binary turned `running 1 test` into `running 2 tests`, and the normalizer masks the integer but not the `s`, so the run reported both `running <int> tests 48 → 49` and `running <int> test 9 → 8` — **ranked above the three real signals**. Those lines are the reporter's own rendering now, so they are not judged. The normalizer is untouched deliberately: a `<int> <word>s` rule would move 108 existing fixture templates (`N seconds`, `N examples`, `N failures`, `N levels`), would still not merge `1 query` with `9 queries`, and would turn `in <int> ms` into `in <int> m<s>`. Every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` replays byte-identical — 438 behaviors and 62 signals unchanged.
  - Upgrading: behavior ids change for every context that runs `cargo test`. Because those runs now carry a test summary and earlier ones do not, the first run after upgrading does not report a flood — it says `no comparable earlier runs (skipped r1…r5: no test summary)` and starts a fresh baseline; the second run compares normally. Nothing stored needs rebuilding, and no context that doesn't run `cargo test` is affected. Two tests of the same name in different test binaries are one behavior whose count is their number, as equally-described RSpec examples already are.

## 0.2.0 — 2026-09-20

- `siftr run` and `siftr ingest` take `--no-report`: siftr prints nothing of its own, ever, while the run is still recorded as normal. Unlike `--quiet-unless-changed`, this holds even when something changed — for a wrapper that must record silently, such as a CI recorder or git hook a developer isn't meant to see. Warnings and errors still print, and the command's own output and exit code are untouched. It's a usage error (exit 2) with `-j`, which always prints its document, and with `--quiet-unless-changed`, which it makes redundant.
- A count that only tracks the suite's size ranks with setup changes instead of heading the report. Adding examples moves whatever runs once inside each of them — rspec's transactional `BEGIN` and `ROLLBACK`, a query every example makes — in lockstep with the example count, so it restates what the NEW examples already say. Over eight runs of someone building a feature, `TRANSACTION ROLLBACK TRANSACTION` headlined both runs that reported anything (`docs/findings/dogfood-junior-loop.md`). Demoted, never dropped: a count that outgrew the suite — two rollbacks per example where there was one — still reports at its own tier, as does one concentrated in a single example. No threshold was added; the demotion asks the same FREQUENCY rule whether the count *per example* moved, and that rule is invariant under scaling every run's value by one factor, so a suite holding its size is judged exactly as it was. Every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` is unchanged.
- LATENCY judges any behavior that carries a duration, not only test examples. siftr times a request, a query and a log line that names its own duration on every run it records, and no rule could read any of it: with `sleep 0.4` added to a controller action, `GET PostsController#index 2xx` went from a 960µs P50 and 9ms of total time to 430ms and 3.32s, plainly visible in `siftr summary`, while `siftr changes` reported `0 changes` (`docs/findings/traffic-vs-dev-loop.md`). For a service under recurring traffic, latency is usually the question, so that was the wrong silence. No threshold moved: the same +100ms floor and 4x ratio, which on healthy traffic sits 114x above the largest run-to-run move measured there (`docs/findings/latency.md`). The adjacent-example veto stays an example's alone, since examples run one at a time and a behavior that recurs through a run has no adjacent anything. The stall guard carries over — it asks whether the behavior's own kind of work slowed around it — now charged in total time rather than per occurrence, since a behavior occurring eight times a run moves its window by eight times its own delta. A request's latency now ranks where an example's does, so on a traffic run the slowdown heads the report instead of sitting below a FREQUENCY on an SQL count. That ranking is inert on the fixtures, none of which produces a request latency, so every scenario reports exactly what it did.
  - Upgrading: nothing to do, and nothing stored needs rebuilding. A context whose runs carry durations outside test examples can now report latency changes it never could before; every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` reports exactly what it did.
- A log line with no test example to belong to is attributed to the HTTP request that produced it, so one regression in server traffic reads as one finding instead of several. Grouping keys on the enclosing example, and a running server has none, so every signal from traffic became its own headline: eight identical requests against a seeded N+1 reported **four separate changes** — the request's query count, the view line that issued the queries, the new query, and the preload that vanished (`docs/findings/traffic-vs-dev-loop.md`). They are now **one change** headed by `GET PostsController#index 2xx  queries 16 → 48`, with the other three as its supporting evidence. A request is scoped by its endpoint (`GET PostsController#index`) rather than by its own behavior, whose status class isn't known until the `Completed` line — after every line the scope has to cover. In `-j`, `attribution.phase` gains `request`, and `attribution.scope` is null for one, since an endpoint is not a behavior siftr records. An enclosing example always wins, so a test run is unaffected: every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` is byte-identical.
- Examples that arrive together in one spec file are one change, as examples that disappear together already were. Adding a spec file reported one NEW change per example it brought — the developer's own deliberate work arriving as a flood of findings, and the bulk of the noise watched over eight runs of someone building a feature (`docs/findings/dogfood-junior-loop.md`). A suite that grew 4 → 10 examples in the run that also regressed reported **8 changes**, six of them examples of the same added file; it now reports **3** — the failure, the deprecation warning, and `6 examples of ./spec/b_spec.rb  new`. One that grew 4 → 20 went from 17 changes to 2. Nothing is dropped or merged away: the examples are still one signal each, still listed in `-j`, still counted by `signals_total`, and the group ranks at its headline's tier, so a real regression still outranks it and an incomplete run still says so first. The grouping is on the spec file the examples share and **never** on how their counts moved, which `docs/findings/grouping.md` measured at a 15% false-merge rate. Only a suite that changed size is affected — every `fixtures/rails_demo` scenario is byte-identical, as is every `fixtures/rspec_hunt` replay whose baseline ran the same examples. `groups[].disappeared_examples` in `-j` is unchanged and still names only the DISAPPEARED half, so nothing reading it needs updating; a collapsed NEW group reads off `groups[].signals` as it always has.
- A request that slowed and a count that moved inside it are one change, not two. Grouping keys on the scope whose own measure moved, and no scope records a duration — so a LATENCY signal had nothing but zeroes to compare, found no scope, and stood alone as a second headline while every count from that same request collapsed under the first. Eight identical requests carrying both an N+1 and a 0.4s sleep in the action reported **two changes** for one cause, `GET PostsController#index 2xx  queries 16 → 48` and `GET PostsController#index 2xx  2ms → 414ms`; they are now **one**, with the slowdown among its supporting evidence (`docs/findings/latency.md` §7). Nothing is dropped or merged away: still five signals, still one each in `-j` and in `signals_total`. A behavior whose every occurrence falls inside one scope now groups under that scope whatever moved, because a sole scope owns the behavior entirely. That cannot disturb a measure scopes do record: a sole scope's value *is* the behavior's own, and every rule needs that value to have moved before it raises anything. An enclosing example still wins over a request, so a test run is unaffected: every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` is byte-identical. Such a signal's `attribution` stays null, since the scope holds no number for a duration and `0 → 0` would read as one.
- `siftr follow` reports each shape on stdin the first time it is seen, while the input is still open: `tail -f log/production.log | siftr follow`. Pointing siftr at a live log used to produce nothing at all — `ingest` reads to EOF before it records or compares anything, and a follow never reaches EOF. It is a pure streaming transform: no run recorded, no baseline compared, nothing stored. That is the deliberate scope, not an unfinished half: choosing a run boundary for a stream nobody closes is a windowing question `docs/findings/log-contexts.md` leaves open, where a whole-log comparison produced 10,362 signals and therefore reported nothing. Reporting a shape only on its **first** sighting is what the measurements support: 100 templates carry 70% of a real log's lines and 1,000 carry 88%, so a follow falls quiet after a short warmup and speaks when something genuinely novel arrives. It does not fall *silent* — the one-off tail keeps trickling, 4.8% of lines on a whole-system log and 0.3% on a narrow one — and a follow that has seen 20,000 distinct shapes says once on stderr that it will report no more. The shapes are the behaviors `siftr ingest` records for the same bytes, from the same normalizer and interpreter chain, so the two can never disagree about what a template is. `-J` prints one compact JSON object per line (`seq`, `stream`, `behavior`, `kind`, `template`); `-j` is a usage error, since a pretty document has one beginning and one end and a follow has neither. Only the template is ever printed, never a raw line, so no `SIFTR_REDACT` setting changes what a follow can disclose. Exits 0 when the input ends, 2 on error. Nothing recorded changed: every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` replays byte-identical.
- A failing `it { … }` is reported as a failure instead of a rename. RSpec writes a one-liner's description from the matcher that ran, *after* the example finishes, so keying `test.example` on those words moved a behavior's identity with its outcome — and `rules::error`, which compares an id against its own baseline, could never fire on one. Four green runs then a break in two examples reported the named one as ERROR and the unnamed one as **NEW + DISAPPEARED**, which is the shape of a rename and invites a developer to dismiss a red suite as a refactor; it is now two ERRORs. Those generated words also carry object addresses, making a fresh behavior every run: **84 of 138 signals across a 44-commit faraday replay** (`docs/findings/oss-corpus.md`) and a signal in **50 of 50** clean comparisons of a 378-example suite (`docs/findings/noise-floor.md`), at a confidence that *rose* as siftr accumulated more evidence the thing was noise. The listener now reports the enclosing group's own words whenever the example declared none — the one fact RSpec has and siftr cannot infer — and identity uses those, marking a description the developer never wrote `<unnamed example>`. A group's one-liners therefore share one behavior whose count is their number, as examples sharing a file and description already do, and the exemplar raw lines still name which one failed. Not the RSpec id or the line number, both of which shift when an example is inserted above. Examples whose author named them are untouched, and every scenario in `fixtures/rails_demo` and `fixtures/rspec_hunt` is byte-identical.
  - Upgrading: behavior ids change for `it { … }` examples — the ones that declared no description of their own. The first run after upgrading reports each affected group's examples DISAPPEARED once and NEW once, then settles as the old templates age out of the baseline. Nothing stored needs rebuilding, a suite whose examples all name themselves is unaffected, and an `rspec.ndjson` captured by an earlier listener replays to exactly the ids it always did.
- `siftr history --scorecard` totals what became of a project's signals by kind: raised, examined, resolved, and how many resolved with no siftr command ever run against them. It counts the same rows `history --signals` prints, over the same window. `examined` means `explain`, `evidence` or `ack` ran on that signal's behavior — recorded as fact in the feedback ledger, not inferred from how fast it resolved — so a change read in the run summary and fixed without asking siftr for more reads as unexamined: the rate is a floor on attention, never a measure of what was ignored. Rates carry only the significant figures their counts back (3 of 4 is `0.8`), and signals siftr can no longer judge are counted apart rather than folded into either answer. `docs/findings/attention.md` records what the ledger can and cannot say, including that no human-use corpus exists yet to point it at.
- LATENCY is harder to earn, in two ways that only ever remove a signal. A duration must now leave its baseline's **range** by twice the range width, exactly as a varying count already had to: a build line reporting 245ms → 1050ms over a baseline that already held 1000ms was news, and is not. And an example LATENCY is vetoed when three *other* examples of the same run slowed by at least half as much — the stall the suite-duration guard could not see, because it asks whether the suite's wall clock moved and on a 46s suite it demanded 27s of unexplained movement before it would veto a 300ms claim. On more than half the false positives measured, that clock had not moved at all, which is why no threshold on it could ever have helped. Over 50 clean runs of a real 335-example suite on a busy machine this goes from 19 comparisons carrying a false LATENCY to 5, and a 1002-example suite from 8 to 0; on a quiet machine nothing changes, and injected regressions are detected at exactly the rates they were. The measurement also corrects what `docs/findings/noise-floor.md` §6 concluded: the rate *is* load-dependent — the same suite gives 19 of 50 at load 14–127 and 0 of 50 at load 4.6 — so `docs/findings/signals.md` §3's budget was fitted on a machine state the docs never named. `docs/findings/latency-cohort.md` has both generators, the rejected alternatives with their numbers, and a prediction re-registered per load regime. Nothing stored changes and no flag moves.

## 0.1.7 — 2026-09-18

- A regression that is fixed and breaks again is reported on every run it returns in, however long ago it was first raised. 0.1.6 said this and only half meant it: the reminder still stopped once the original signal's run left the 10-run baseline window, so a change that kept flapping went silent on its sixth return with the regression plainly present, and a CI gate keyed on `changes` and `open_signals` passed exactly that build. Expiry is now a property of the change rather than the age of the signal — one that keeps returning never settles, while one nobody ever fixed still stops being reported about 10 runs on, once every run siftr compares against has it. No rule, threshold or confidence formula moved, and the backtest is byte-identical.
- The `-j` contract for `changes`, `run` and `ingest` says what `open_signals` now covers: any earlier retained run, not only those in `baseline_runs`.

## 0.1.6 — 2026-09-17

- A regression that is fixed and breaks again is reported every time it returns. The rolling baseline absorbs a value it has already seen — a repeat sits inside the baseline's own range, so no per-run rule can fire on it without firing on values the baseline really exhibited — and the still-open reminder, which judges against the signal's frozen original baseline, was dropping it: a change that had been fixed and returned counted as `recurred` rather than `open`, and only `open` was reminded. So the second break of a regression went unreported by every per-run command, while `siftr summary` showed it plainly. A change present at this run is now surfaced whether or not it was fixed in between. The rules and their thresholds are untouched, and the zero-false-positive backtest is unchanged.
- `siftr history --signals` carries every cycle instead of freezing after the first recurrence, and reports the latest verdict: a change fixed, broken and fixed again reads `resolved`, not `recurred`. A new `recurrences` field counts the returns; `resolved_in` and `recurred_in` still name the first of each.
- The change report names the baseline behind each change (`3 baseline runs`) where it printed `conf 0.80`. That score was `(n+1)/(n+2)` over the same count for every kind but LATENCY, so it implied a precision it never had: measured over the backtest corpus it ranks true findings below chance and has never broken a tie. `-j` and `siftr explain` still carry the number, and `docs/findings/confidence.md` records the measurement. Anything grepping `conf ` in human output needs updating.
- `siftr status` lists config files as `looked in … (nothing to read)` rather than `files … (not read)`, which read as though siftr had found them and ignored them.
- The README says what a reminder is bounded by: a change left in place is reminded on every run until the run that raised it ages out of the baseline window, after which siftr calls it normal. It also no longer suggests `[.signals[0]]` for a CI gate, which yields `[null]` rather than `[]` on a run with no signals, and it names the context rule — project root plus the command as typed — before anything else rather than in Limitations.
- `siftr explain` shows a truncated run's event counts instead of a dash per run. `events_past_cap` is the overflow behavior's own count rather than a stored measure, so the values row had nothing to read and printed `events_past_cap r4 -  |  baseline r3 -  r2 -  r1 -` for a signal whose own summary line said 60.

## 0.1.5 — 2026-09-17

- A run whose comparison produces more than 1000 signals records none of them and says so in one line, keeping its behaviors and captured lines as evidence. That many signals says a source's behaviors don't recur, rather than naming findings: pointed at the macOS unified log, siftr produced 8,952 signals from a single five-minute window. Such a run baselines normally, and stays complete unless it was also truncated; `uncompared` in `-j` carries the count that was refused. The bound is a backstop, not a tuning knob — the most a real RSpec suite produced here was 11.
- A run that could not record what it saw never reports itself complete. Truncation past the 20,000-behavior cap belongs to the run, but `complete` was read from the run's recorded signals — so a truncated run that recorded no INCOMPLETE read as complete: a first run of a context, which has no baseline to compare against, and a run whose flood of signals was refused, which records no signals at all. The worse run looked the cleaner one: a run that lost 4,500 events and refused 20,001 signals printed `0 changes` with no `incomplete` marker, beside strictly less broken runs that carried one. `complete` now reads the run's own truncation, in `-j` and in the `siftr history` marker alike.
- The refusal threshold counts signals, not the changes they group into, and now says so: `1017 signals, too many to be findings, so no changes were recorded`. The two differ by design — the demo suite's N+1 is 4 signals in 1 change, and 1,000 same-prefix stderr messages are 1,000 signals in 1 change — so a run can be refused at 1,001 signals when the change it had to report was exactly one. Nothing about when a run is refused has changed: the bound was always on signals, which is what the measured separation (11 against 8,564) was measured in.
- `siftr changes` and `siftr summary` say `1 event`, not `1 events`, in the note about behaviors past the cap.
- `siftr history --sources` shows what each run actually read, in human and `-j` output. `not recorded` (`sources: null`) means the run recorded no sources, so siftr cannot say what it read — not that it read nothing: `ingest` replays a capture rather than choosing sources, so an ingested run always reads that way.
- `docs/json.md` describes every command's `-j` document field by field, including the shapes that differ between commands — three commands return a bare array, and `history --signals` nests a signal where `changes` inlines one. `siftr --help` and the README point at it.
- A run whose behaviors hit the 20,000-behavior cap no longer reports what the cap cut as behavior appearing or disappearing. Past the cap a behavior is kept on the arrival order of its first occurrence, so the same lines in a different order disagreed about what exists: one 20,060-line corpus replayed with its first 60 lines moved to the end reported 60 NEW and 60 DISAPPEARED, from content identical line for line. Such a run now says once that it was truncated, as INCOMPLETE, and raises nothing from its absences — while what it did keep is still judged, since a kept behavior's counts are exact. Test examples and summaries are exempt from the cap, so a deleted spec file is still reported. A real suite is nowhere near this: the demo suite produces 46 behaviors.
  - Upgrading: nothing to do, and nothing stored needs rebuilding. A context whose runs exceed the cap will report those runs INCOMPLETE (`complete: false` in `-j`) where it previously reported changes; a context under the cap is unaffected.
- A later run that could not judge absences no longer resolves an earlier DISAPPEARED. A truncated run raises nothing from its absences, and that silence was being read as the behavior coming back; such a run, and one whose comparison was refused for producing too many changes, no longer votes on whether an earlier change is still there.
- A run whose comparison was refused no longer reminds of earlier changes still open, and no longer exits 0 as though it had found something. Judging those would re-run the comparison siftr declined to report.
- `siftr changes -n N` shows the N highest-ranked changes, in human and `-j` output. It has no default: without it the report is complete, as before. `changes -j`, `run -j` and `ingest -j` gained `groups_total` and `signals_total` — the run's own counts whatever the document lists — so a consumer can tell a limited report from a whole one.
- A truncated run says what the cap cost in words: `60 events past the 20000-behavior cap`, and `so this run's absences weren't judged`, rather than `events_past_cap 60`.

## 0.1.4 — 2026-09-16

- A run records which sources it actually read, and a behavior whose source was absent from one side of a comparison no longer raises NEW or DISAPPEARED. Turning `[sources.rails_log] enabled = false` on or off in `.siftr.toml` changes what siftr looked at, not what your command did, and siftr no longer reports the difference as behavior appearing or disappearing. The migration runs automatically and runs recorded before it compare exactly as they did: DISAPPEARED is protected from the first run after upgrading, NEW once the baseline window has been re-recorded. A count that moves because a source was switched off is still reported, since attributing part of a count to one source would be a guess.
- `siftr run` and `siftr sources` no longer run a flag you mistyped. An unknown flag before `--` filled the wrapped command instead of failing to parse, so `siftr run --qiet -- rspec` tried to execute `--qiet` and exited 127 — pointing you at your command rather than at your typo. It is now a usage error, exit 2, naming the flag and suggesting the near match, as an unknown word has been since 0.1.2. Everything after `--` is still the wrapped command's own: `siftr run -- ls --typo` still passes `--typo` to `ls`.
- A log statement no longer splits into one behavior per weekday or per machine. siftr masks a ctime weekday (`Thu Sep 10 00:33:52.607 …`) and the host after an ISO-8601 timestamp (`2026-09-10 00:33:52.607000-0700 host proc[pid]: …`), both of which it previously kept. On three days of a real `wifi.log` that takes 154 behaviors to 61, and a hostname no longer reaches a stored template — where `SIFTR_REDACT=pii` could not reach it. A weekday anywhere but at the head of a timestamp is untouched, as `Scheduled for May` has been since 0.1.2.
  - Upgrading: behavior ids change for lines that start with a ctime weekday, and for ISO-8601 lines carrying `host proc[pid]:`. In a context whose source has either shape, the first run after upgrading reports those behaviors DISAPPEARED once and NEW once, then settles as the old templates age out of the baseline. Contexts whose sources carry neither shape — RSpec suites, Rails logs, BSD syslog — are unaffected, and nothing stored needs rebuilding.

## 0.1.3 — 2026-09-16

- `siftr sources` says what siftr can read here: the command's own output, and everything else a run produces — RSpec's per-example events (`rspec`), the slice of `log/test.log` a run appends (`rails_log`), and what the kernel charged the run (`rusage`). Each row gives the source's name, whether it's on, whether it applies to the command you name, and why either way (`the command isn't an rspec run`, `no log/test.log, and no Gemfile naming rails`). A source is named by its configuration key, so the word you read is the word you set. What applies depends on the command as much as on the directory, so `siftr sources -- bundle exec rspec` answers precisely; with no command it judges the directory alone and says so. Read-only: it prepares nothing, runs nothing and records nothing. Exits 0.
- `run -j` and `ingest -j` carry `streams`: what the run actually captured, spelled as an exemplar's `stream` is (`stdout`, `stderr`, `file:rspec-events`, `file:log/test.log`), so a piece of evidence joins straight to it. A stream opens on its first byte, so a command that wrote nothing to stderr doesn't list it. `changes -j` reports `streams: null`, since the store doesn't hold what a run read. A source that was expected and failed warns as before, now naming itself — `rspec skipped: …` rather than `side channel skipped: …`.
- A project can turn siftr's sources off in a file. `.siftr.toml`, found by walking up from where you run siftr and stopping at the project root, then `~/.config/siftr/config.toml` (`$XDG_CONFIG_HOME` honored). It holds one thing:

  ```toml
  [sources.rails_log]
  enabled = false
  ```

  Every source is on unless a file says otherwise, and the project file wins over the user file. Nothing else goes in the file: retention (`SIFTR_KEEP_*`) and privacy (`SIFTR_REDACT`, `SIFTR_CAPTURE`) stay environment-only, since they're about your machine and the data dir every project shares, not about one project. An unknown key, an unknown source name, a value of the wrong type, or a file that isn't valid TOML warns once on stderr and leaves the default standing: your command still runs and still exits with its own code.
- `siftr status` has a `config` block: what each source is set to, which file set it (or `default`), and which files siftr looked for — so a file that isn't taking effect says so instead of being silently ignored. In `-j` it's `config.sources` and `config.files`.
- siftr records what the kernel charged every run: CPU time (user and system), peak memory, and voluntary and involuntary context switches. One `getrusage` of the reaped child, ~0.19µs, no sampler — and no change to how your command runs, what it prints, or the code it exits with. A command that exited non-zero or died from a signal is measured too. It's a source like the others: `[sources.rusage] enabled = false` turns it off.
  - **This is evidence, never a signal.** CPU and memory vary far too much run to run to judge — `docs/findings/signals.md` §1 measured a suite's wall time spanning 10x — so `run.resources` is the one behavior kind no rule reads. It cannot raise a change, whatever the numbers do.
  - Upgrading: nothing to do. The first run that records it isn't reported NEW, and a run recorded with the source off isn't reported DISAPPEARED, for the same reason.
- `siftr explain` shows the run's CPU and peak memory beside the median of its baseline runs, so a slowdown that came with far more CPU or far more preemption reads as a loaded machine rather than a code change; `siftr evidence` shows the line the numbers came from. In `-j` that's `explain`'s `resources` {`current`, `baseline`}, in whole milliseconds and bytes on every platform — `ru_maxrss` is bytes on macOS and kibibytes on Linux, and siftr normalizes it at the syscall. Only fields the platform actually fills are reported: macOS leaves the disk-I/O counters at zero even for a child that fsync'd 64 MiB, so siftr reports none rather than zeros dressed as data.
- `siftr evidence` lists only the captures still on disk. A run recorded with `SIFTR_CAPTURE=off`, or one whose captures retention has since pruned, was given a `capture stdout: …` line naming a file that was never written; `-j`'s `captures` carried the same dead paths. Both now list what you can actually open, and nothing when that's nothing.

## 0.1.2 — 2026-09-15

- `siftr` without a subcommand does the obvious thing, and never guesses. `siftr -- CMD` is `siftr run -- CMD`. `siftr FILE` (or `siftr -`) ingests it, compared only with earlier ingests of that file; `--context NAME` still wins, for dated or rotated files. A bare `siftr` ingests stdin when it's piped or redirected, and prints help otherwise. A subcommand or preset always wins over a file of the same name (`./cron` names the file). Any other word is an error with a "did you mean", exit 2, never read as a file. `siftr ingest FILE` is unchanged and still compares within the `ingest` context.
- System logs no longer split one message into a behavior per day, host or connection. A syslog line's header (`Sep 14 10:21:07 mbp-a backupd[412]:`) becomes `<timestamp> <host> backupd[<int>]:`, so a new month or another machine is the same behavior; the process name stays as written. A month word anywhere else (`Scheduled for May`) is untouched. A `0x` pointer glued on by a dot (`peer[3].0x7fa1c2`) is masked like any other `0x` value.
  - Upgrading: behaviors from syslog lines, and from lines with a dot-glued `0x` value, get new ids. The first run after upgrading reports them NEW and their old spellings DISAPPEARED; the run after compares normally.
- macOS `log show` and `log stream` column headers (`Timestamp  Thread  Type …`, in the default, compact and syslog styles) are no longer a behavior, which appeared in every run even when nothing matched. The first run after upgrading compares normally: a behavior present in every baseline run and absent now needs n ≥ 2, so expect one DISAPPEARED on that header in a context with 2 or more earlier runs.
- `siftr history` says `1 line`, not `1 lines`.
- `siftr cron` shows what runs on a schedule (your crontab, `/etc/crontab`, `/etc/cron.d`, and launchd user agents on a calendar or interval) and where cron's output goes (the mail spool, `/var/log/cron`, syslog, the macOS unified log), with the line that records each crontab job through `siftr --`. It's read-only: it edits no crontab or agent, runs no job, and records nothing. Exits 0 when it found a job or cron output, 1 when it found neither.
- `siftr run` and `siftr ingest` take `--quiet-unless-changed`: siftr prints its report only when the run has a change (INCOMPLETE included) or one still open, and nothing otherwise, first runs included. A job wrapped for cron, CI or a git hook then prints only what the command did; cron mails nothing from siftr until something changes. A still-open change is reported every run until it's fixed or `siftr dismiss`ed. Warnings (a run not recorded) and errors always print, and the command's output and exit code are untouched. `siftr cron`'s record-it lines use it. With `-j` it's a usage error (exit 2), since `-j` always prints its document.

## 0.1.1 — 2026-09-15

- A path in a log line no longer ties a behavior to the machine or directory it ran in. Where the path lives is canonicalized: the project root to `<root>/`, a home to `~/`, a temp dir to `<tmp>/` (with the names generated in it as `<tmpname>`), an installed gem, crate or npm package to `<gem:name>/`, `<crate:name>/` or `<npm:pkg>/`. What it names stays, so one deprecation warning on a laptop and in CI is one behavior, and upgrading a gem doesn't make its backtrace lines new.
- Behaviors carry what their paths are (database, lock, manifest, log, test, source, view, config, dependency, temp), in `summary` and `explain` and as `behavior.roles` in `-j`. Nothing is signalled on them.
- **Security:** siftr 0.1.0 stored credentials from a command's output verbatim: in behavior templates (never pruned), kept lines and raw captures. siftr now masks every credential it recognizes before anything reaches disk: GitHub, GitLab, AWS, Google, Slack, Stripe, npm, SendGrid and OpenAI-style tokens, JWTs, private keys, `Authorization` values, URL passwords, cookie values, and high-entropy values under keys like `password`, `api_key`, `access_token` or `SECRET_KEY_BASE`, including Rails SQL binds and JSON. Placeholders are numbered per run (`<TOKEN_1>`, the same number for the same value); templates drop the number, so a behavior doesn't change with the credential. The command's own output still passes through unchanged. Commands, contexts and `ack`/`dismiss` notes are masked too.
- `SIFTR_REDACT=pii` also masks emails, public IPs and home directories in raw captures and kept lines; `SIFTR_REDACT=off` keeps raw captures as they were (the database still never holds a credential). `SIFTR_CAPTURE=off` writes no raw capture; `explain` and `evidence` then show kept lines instead of a failure's whole message. Behavior ids don't depend on either setting.
- A raw capture keeps a line over 1 MiB only up to 1 MiB, as siftr analyzes it.

### Upgrading

- Baselines reset once for commands whose output contains absolute paths: the first run after upgrading may report those behaviors as NEW and their old spellings as DISAPPEARED. The run after compares normally.
- The first siftr to open an existing data directory redacts what it holds in place (templates, kept lines, commands, notes) and **deletes every raw capture recorded before**. Old runs keep their numbers and kept lines; `explain` on them shows kept lines instead of whole messages. It takes about 1 µs per kept line, once: 0.23 s for a store of 200,000 (`docs/findings/redaction.md`); another siftr opening the store meanwhile waits up to 2 s, then runs its command unrecorded. Behaviors whose template held a credential are NEW once, and their old ids DISAPPEARED. SQLite may keep freed pages holding old text until `siftr gc` vacuums it; to be sure, run `siftr gc` after upgrading. Anything copied out of the data directory before is not touched.

## 0.1.0 — 2026-09-15

First version. If you ran a pre-release build, see **Upgrading** below.

- `siftr run -- CMD` runs a command, passes its output through unchanged (colour included, via a PTY), exits with its code, and prints what changed since recent runs of the same command to stderr.
- RSpec + Rails: per-example results come from a reporter listener added through `SPEC_OPTS` (your formatters are untouched), and SQL and request lines from the slice of `log/test.log` the run wrote.
- Signals: ERROR, NEW, DISAPPEARED, FREQUENCY (SQL counts, per-request and per-example query counts) and LATENCY (a single example, at least +100ms and 4x). Related signals are grouped under one headline. Confidence comes from the size of the baseline.
- `changes`, `explain`, `evidence`, `summary`, `history` to drill from a change to the raw lines behind it. Every command takes `-j`.
- `siftr ingest` records a file, stdin, or a captured scenario directory (`--dir`) as a run.
- Ctrl-C'd runs are kept for evidence but never used as a baseline.
- `siftr ack <signal> [-m TEXT]` and `siftr dismiss <signal> [-m TEXT]` record whether a signal is being acted on or isn't worth it.
- `siftr history --signals` shows what became of recent signals — open, resolved (after investigation or without), recurred — each judged against its original baseline, so a regression the rolling baseline has absorbed still reads as open.
- siftr keeps a local record of how its signals are used (shown, explained, evidence requested, acked, dismissed) so it can later learn which signals matter. Nothing leaves the machine.
- Two siftr processes opening a new data directory at once no longer race.
- siftr deletes old data. Per command it keeps stats for the last 100 runs (`SIFTR_KEEP_RUNS`) and exemplar lines plus raw captures for the last 20 (`SIFTR_KEEP_EVIDENCE`); a command not run for 30 days is forgotten (`SIFTR_KEEP_DAYS`). Reading something pruned says so and names the setting.
- `siftr status` shows what the data dir holds and what retention will do; `siftr gc [--dry-run]` prunes now and reclaims space.
- A log side stream's capture is `file-log_test.log`, not `file-log_test.log.log`.
- A killed or interrupted run is never used as a baseline, nor is a run recorded by an older siftr, so one bad run can't hide the next regression. (Runs that skipped examples: see below.)
- An incomplete run reports one INCOMPLETE change (e.g. the spec file that failed to load, with its error) instead of everything it didn't get to run.
- A command killed by a signal counts as interrupted. siftr stops waiting on leftover background output about a second after the command exits. If the data directory can't be used, the command still runs — unrecorded, with a warning.
- SQL logged between or after examples is attributed as such rather than as setup, and attribution no longer drifts after CRLF or very long log lines.
- `-j` always prints one JSON document: empty results (exit 1) and errors, argument errors included (`{"error":{"code","message"}}`, exit 2).
- An unfixed regression the rolling baseline has absorbed shows as `still open:` in `run`, `ingest` and `changes` (`open_signals` in `-j`) until it's fixed or dismissed.
- Reports name skipped baseline runs and why (`skipped_runs`), and say when a run was incomplete (`run.complete`). `explain` and `evidence` show a failure's whole message.
- Changes outside examples say whether they happened before, between or after them. In `-j`, `attribution.setup` is now true only for setup; use `attribution.phase`.
- Two apps in one repository no longer share a baseline: the project is the nearest directory with a manifest (Gemfile, Cargo.toml, package.json, …), else the current directory.
- A run is left out of a baseline only when it skipped examples this run ran (a failed spec file, `--fail-fast`, a focus filter). A suite that grows or shrinks, a red `--fail-fast` suite, or fixing a spec file that never loaded no longer hides a regression landing in that run.
- A run is INCOMPLETE only when it skipped examples its baseline ran; deleting spec files is a real change, not a partial run. A load error names the file and Ruby's cause: `./spec/x_spec.rb failed to load: SyntaxError: …`.
- `history --signals`: a focus or load-error run no longer counts as resolving a signal, and INCOMPLETE is never listed as still open. `history` marks incomplete runs, and `history --context <unknown>` exits 2 like `changes`.
- A busy data directory no longer holds up `siftr run` indefinitely: if another siftr holds it for more than 2s, the command runs unrecorded, with a warning saying why.
- Runs whose command was killed by a signal (exit 129–159) never join baselines, including runs recorded by older builds.
- Retention never prunes a run that is still recording, and beyond the limits it keeps whatever the latest run still compares against: its baseline runs, their own baselines, and the evidence a still-open reminder points `explain` to. When a signal's evidence was pruned anyway, `explain` shows its numbers and says so rather than failing.
- `siftr run -- CMD | head` stops the command as it would unwrapped: the command gets SIGPIPE, siftr exits the same way, and the truncated run is kept out of baselines.
- A busy store never delays the command's start or its output; if it stays busy, the run passes through unrecorded with one warning. `siftr run -j` prints a JSON document even then (`run: null`, `not_recorded: {code, message}`), and `busy` is a JSON error code for every command.
- When earlier changes are still open, the run header says `no new changes · N still open` instead of `0 changes`.
- A new error outside examples — a `raise` after a describe block, a suite hook that raises — is a NEW change even when every example ran.
- Deleting or renaming a spec file is one change (`N examples of <file>`), not one per example, and never outranks a real regression. Still-open reminders no longer repeat examples or queries that disappeared on purpose; a DISAPPEARED signal supporting a regression still rides with it.

### Upgrading

- An app below its repository root, or a directory in a repository with no manifest, starts a fresh baseline once ("no earlier runs"). Runs at a repository root with a manifest keep theirs.
- Runs recorded before this version carry no count of defined examples; a smaller one is still judged by which examples it ran, so right after a suite grew it may be skipped until it ages out of the last 10 runs.
- The first command after upgrading migrates the database — seconds on a large store. Then run `siftr gc` once to prune the backlog and shrink the file; until you do, each run prunes a bounded amount.
